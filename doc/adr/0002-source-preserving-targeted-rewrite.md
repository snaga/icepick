# 0002. 差分生成ロジックの刷新：AST全行再フォーマットから元ソース書式保持型局所置換（TextSplicer）への移行

* **ステータス**: Accepted
* **決定日**: 2026-09-13

---

## 1. 背景と課題 (Context)

従来の Icepick では、`icepick rewrite <file>` による最適化パッチ生成において、以下のプロセスを採用していました：

1. 元の SQL ファイル（生テキスト）を `sqlglot` で AST（抽象構文木）にパース。
2. AST 上でアンチパターンを検出・置換（`node.replace()` / `node.pop()`）。
3. 最適化後 AST を `ast.sql(pretty=True)` で SQL 文字列に再シリアライズ。
4. 元 SQL も `ast_orig.sql(pretty=True)` に正規化し、`format_diff(ast_orig, ast_opt, normalize=True)` で Unified Diff を生成。

しかし、この方式は**エンタープライズの現場において深刻な摩擦（Friction）と不整合**を引き起こしていました：

1. **クエリ全体のフォーマット汚染とノイズ差分**:
   - `ast.sql(pretty=True)` を通した時点で、`sqlglot` の既定フォーマット（2スペースインデント、大文字キーワード、独自の改行）でクエリ全行が書き換わってしまう。
   - エンタープライズ開発で一般的な「4スペースインデント」「小文字キーワード」「丁寧な行内・行頭コメント」「空行による論理ブロック分離」がすべて破壊され、Git blame やコードレビューで膨大なノイズ差分が発生した。
2. **パッチ適用エラー (`Hunk rejected` / 行不一致)**:
   - 出力された `.patch` は「2スペースインデントの架空コード」に対する差分であるため、ユーザーの「元の生ファイル（4スペースインデント）」に対して `icepick patch` や `git apply` を実行すると、コンテキスト行が一致せずパッチ適用が失敗（`ValueError: Hunk target lines could not be matched`）した。

---

## 2. 決定事項 (Decision)

### ① 元ソース書式保持型局所置換エンジン (`TextSplicer`) の導入
- クエリ全体を AST から再フォーマットして diff を取る方式を廃止します。
- 代わりに、**「① 元の生の SQL テキスト」をメモリ上で維持し、AST 診断で特定された患部ノードの該当スパンのみをピンポイントで外科手術置換した「② 修正後生テキスト」** を構築する `TextSplicer` を導入します。
- `difflib.unified_diff(①, ②, normalize=False)` を実行することにより、**「元ファイルの生コードに対する完全一致 Unified Diff」** を生成します。
- 複数箇所の置換において文字オフセットがずれるのを防止するため、Issue は**開始位置の降順（ファイル末尾から手前へ）**にソートして置換します。

### ② パッチ適用エンジン (`apply_unified_diff`) のインデント自動再調整
- 外部作成パッチや旧フォーマット差分でも安全に適用できるよう、`_find_matching_position` に多段フォールバック（`完全一致` ➔ `rstrip` ➔ `strip（インデント非依存）` ➔ `Fuzzyトークン正規化`）を導入します。
- 行頭インデントの差異（2スペース vs 4スペース、タブ）を自動検出し、挿入行（`+` 行）のインデントを元ファイルのスタイルに合わせて自動再調整（Indent Re-targeting）して適用します。
- コンテキスト行（` ` 行）は元ファイルの生テキストを 100% 維持して書き出します。

### ③ 全体再フォーマットフォールバック (`--reformat`)
- チーム規約に合わせて AST 全体を綺麗に整形（pretty-print）したい場合、または CTE 平坦化（`--flatten-subqueries`）などの全体構造組み換えを伴う操作のために、`--reformat` フラグを明示的に指定した場合は従来の全行 AST 再フォーマット Diff（`normalize=True`）を許可します。

---

## 3. 影響と評価 (Consequences)

### メリット (Positive)
- **修正点の真の最小化**:
  - 1,000行のクエリのうち、修正対象の数行以外は、元のインデント（4スペース等）、コメント、改行、小文字キーワードが **1文字も改変されずに 100% 維持**されます。
- **パッチ適用の 100% 成功保証**:
  - 生成されたパッチのコンテキスト行が元ファイルと完全一致するため、`icepick rewrite file.sql -o file.patch` ➔ `icepick patch file.sql file.patch` がエラーなく吸い付くように適用可能になります。
- **Git レビュー負荷の極小化**:
  - 不要な空白・インデント差分がゼロになり、PR / MR レビューアは「どのビジネスロジック・SQLアンチパターンが最適化されたのか」のみを即座に確認できます。

### トレードオフ・デメリット (Negative / Mitigation)
- **複雑な構造変換の制約**:
  - サブクエリの CTE 外出し（`SNOW-007` / `--flatten-subqueries`）のように、クエリ全体の構文木組み換えを伴う操作はテキスト局所置換だけでは対応できません。
  - *対策*: 構造組み換え時および `--reformat` 指定時は、明示的に AST 全体再フォーマットモードへ自動フォールバックするハイブリッド設計とします。
