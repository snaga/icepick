# 0004. Snowflake 直接接続の廃止と等価性検証 SQL 生成（Verify Generator）への責任分離

* **ステータス**: Accepted
* **決定日**: 2026-09-13

---

## 1. 背景と課題 (Context)

Icepick では、最適化前後のクエリが同一の実行結果を返すことを保証するため、`icepick verify` コマンドおよび `rewrite --verify-loop` において、Snowflake への直接接続と双方向 `EXCEPT` クエリの自動実行を行っていました。
しかし、開発を進める中で以下の設計的・運用的な課題が顕在化しました：

1. **ツールの責務肥大化と複雑性の増大 (Scope Creep)**:
   - 「AST Query Optimizer / Linter（構文解析と最適化パッチ生成）」というコアバリューに対し、Snowflake Python ドライバ依存、アカウント・DB・スキーマ・ウェアハウス・ロール等の接続パラメータ管理、WCM ペア認証（`icepick:snowflake`）、ネットワーク接続リトライ・タイムアウト処理など、データベース接続クライアントとしての重厚な責務を抱え込んでいた。
2. **エンタープライズ導入におけるセキュリティ・ネットワーク障壁**:
   - 企業の実環境では、本番・検証 Snowflake への接続は Okta SSO、MFA、社内プライベートプロキシ、AWS PrivateLink、CyberArk などの特権アクセス管理を経由することが標準である。
   - サードパーティ製 CLI が直接データベースのパスワードを保持して接続する形態は、セキュリティポリシー審査の大きな障壁となっていた。
3. **AI エージェント時代におけるパイプライン統合の摩擦**:
   - 現代のワークフローでは、人間が単一コマンドで全自動実行するよりも、AI コーディングエージェント（Claude Code, Antigravity 等）がツールを組み合わせて自律的に作業を進める形態が主流となっている。
   - エージェントにとっては、内部で閉じたブラックボックスな接続ループよりも、UNIX 哲学（単一責任の原則 / Do One Thing and Do It Well）に従い、標準出力やファイル経由で公式 CLI（`snow CLI` 等）と疎結合にパイプ連携できる方が圧倒的に制御しやすく、トラブルシュートも容易である。

---

## 2. 決定事項 (Decision)

### ① `icepick verify` の責務を「等価性検証 SQL 生成」に純化
- `icepick verify <orig.sql> <opt.sql>` は、Snowflake への直接接続・実行を行わず、**2つのクエリが等価であるかを決定論的に判定するための双方向 `EXCEPT` 検証クエリを生成・出力する単一責任ジェネレーター**に刷新します。
- 出力先として標準出力（デフォルト）およびファイル出力（`-o, --output <file>`）をサポートします。
- クエリ形式として、完全一致行差分を返す標準モードと、差分件数のみを返す集約モード（`--count-only`）を提供します：
  ```sql
  -- Icepick Equivalence Verification Query (Generated by icepick verify)
  -- Returns 0 rows if both queries are semantically equivalent.
  WITH orig AS (
    SELECT ... FROM ...
  ),
  opt AS (
    SELECT ... FROM ...
  )
  SELECT 'orig_not_in_opt' AS diff_type, * FROM (
    SELECT * FROM orig EXCEPT SELECT * FROM opt
  )
  UNION ALL
  SELECT 'opt_not_in_orig' AS diff_type, * FROM (
    SELECT * FROM opt EXCEPT SELECT * FROM orig
  );
  ```

### ② データベース実行責任の公式ツール・外部環境への委ね
- クエリの実行そのものは、Snowflake 公式の **`snow CLI` (`snow sql -f verify.sql`)**、`dbt`、社内 CI/CD パイプライン、または既存の認証済み接続基盤に委ねます。
- AI エージェントやシェルからは、以下のように極めてシンプルにワンライナー連携が可能です：
  ```powershell
  icepick verify orig.sql opt.sql | snow sql -f -
  ```

### ③ 自己修復ループ（Verify Loop）のオーケストレーション主体を外部エージェントへ移行
- `icepick rewrite` 内部で Snowflake 接続を抱え込む自己修復ループは廃止し、上位のオーケストレーター（AI エージェント）が外回りループとして自律制御する設計に移行します：
  1. `icepick rewrite query.sql -o changes.patch`（最適化パッチ生成）
  2. `icepick verify query.sql opt.sql -o verify.sql`（検証 SQL 生成）
  3. `snow sql -f verify.sql`（社内環境で検証クエリ実行）
  4. 差分があれば、エージェントが差分情報をプロンプトに含めて再度 `icepick` を呼び出す。

### ④ Snowflake 依存パッケージ・認証管理の完全撤退
- `snowflake-connector-python` への依存をパッケージから完全削除します。
- `Config` および環境変数マッピングから `snowflake_*` 関連パラメータを撤廃します。
- WCM の `icepick:snowflake` ペア認証管理ロジックを廃止し、Icepick が扱う機密情報を「LLM プロバイダ認証（Gemini API キー / GCP ADC）」のみにスリム化します。
- `icepick config test` は LLM 接続診断に特化させます。

## 3. メリットとトレードオフ (Consequences)

### メリット (Pros)
- **ゼロ・DB 認証情報**: データベースのパスワードや認証トークンを一切扱わないため、エンタープライズのセキュリティ審査がフリーパスになる。
- **超軽量・超ポータブル**: 重厚な C 拡張ドライバ（`snowflake-connector-python`）が不要になり、あらゆる環境で数秒でインストール・実行可能。
- **高い信頼性と保守性**: ネットワーク瞬断、VPN 切断、ドライバ互換性問題、Snowflake 認証切れによるエラーハンドリングが消滅し、コードベースとテストの複雑度が半減する。
- **エコシステム親和性**: 既存の社内接続設定（Snowflake CLI 構成ファイル、環境変数、SSO トークン）をそのまま再利用可能。

### トレードオフ・考慮事項 (Cons & Mitigation)
- **手動ワンライナーの分離**: 人間が直接実行する場合、`icepick verify` と `snow sql` を組み合わせるステップが必要になる。
  - *Mitigation*: CLI ヘルプおよび README に `snow sql` や `snowsql` とのパイプ連携コマンド例を明記し、AI エージェント向けの明確なシステムプロンプト例を提供する。
