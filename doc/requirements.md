## 概要

本システム（Icepick for Snowflake、CLI名: icepick）は、Snowflake環境で実行される長大バッチクエリに対し、AST（抽象構文木）を用いた決定論的なアンチパターン診断と、ピンポイントなIn-place置換（ルールベースおよび局所LLM連携）を実施し、Git互換のUnified Diff形式で差分を提示・適用するCLIツールである。

## 前提条件

- 入力されるSQLは、Snowflakeの方言（Dialect）として構文的に有効であること。
- Python 3.10以上の実行環境および `sqlglot` ライブラリが利用可能であること。
- LLMによる局所リライト機能（--agentic）を利用する場合、Gemini APIキーまたはGoogle Cloud ADC（Vertex AI）の認証情報が利用可能であること。
- 等価性検証用 SQL（icepick verify）を Snowflake 実環境で実行・突合する場合、外部の公式ツール（snow CLI 等）や適切な実行環境が用意されていること（Icepick 本体は DB 認証情報を一切保持・要求しない）。

## 制約条件

- 構文エラーを持つ入力SQLに対しては、ファイルを変更せず明確なエラー行番号を出力して終了しなければならない。
- 最適化処理において、対象外の健全なASTノードの構文構造・論理セマンティクスを一切破壊してはならない。
- 差分出力は、標準的なGit diffツール（`git apply` 等）で解釈可能なUnified Diff形式に厳格に準拠しなければならない。

## 要件

### 要件カテゴリA: 構文解析と決定論的静的診断 (Linter)

- 要件 A-1: Snowflake SQLパース
   - ユーザーストーリー
      - 私はデータエンジニアとして、Snowflake特有の構文を含むSQLファイルを読み込みたい。なぜなら正確な構文木として解析するためだ。
   - 受け入れ基準
      - ユーザーがSQLファイルパスを指定して `icepick diag <file>` を実行したとき、システムは `sqlglot` を用いてSnowflake方言としてASTを構築しなければならない。
      - もし入力SQLに構文エラーが含まれる場合、システムはエラー発生箇所の行番号とトークン情報を表示し、非ゼロの終了コードで終了しなければならない。


- 要件 A-2: Non-Sargable述語の検出 (SNOW-001)
   - ユーザーストーリー
      - 私はデータエンジニアとして、パーティションプルーニングを無効化しているWHERE句を検知したい。なぜなら無駄なフルスキャンを防ぐためだ。
   - 受け入れ基準
      - AST走査時にWHERE句内のカラムに対する関数適用比較（例: `DATE(col) = '...'`）が存在するとき、システムは `SNOW-001` 警告として該当ノードの行番号とコードスニペットを出力しなければならない。

- 要件 A-3: 相関副クエリの検出 (SNOW-002)
   - ユーザーストーリー
      - 私はDBAとして、反復評価やメモリSpillを引き起こす相関副クエリを検知したい。なぜならクエリ実行時間の爆発を避けるためだ。
   - 受け入れ基準
      - AST走査時にWHERE句（EXISTS, IN, 比較述語）またはSELECT句内のサブクエリが外側クエリ（外側SELECT/CTE）のテーブル名またはエイリアスを参照するカラム条件を含むとき、システムは `SNOW-002` 警告として重要度 `CRITICAL`、`requires_llm=True` をセットして出力しなければならない。
      - サブクエリ内部のテーブルのみを参照し外側スコープを参照しない独立した非相関サブクエリ（Uncorrelated Subquery）が存在するとき、システムは `SNOW-002` として誤検知してはならない。

- 要件 A-4: サブクエリ内の不要なソートの検出 (SNOW-003)
   - ユーザーストーリー
      - 私はデータエンジニアとして、サブクエリ内にある無意味なORDER BYを検出したい。なぜならオプティマイザの負荷とメモリ消費を削減するためだ。
   - 受け入れ基準
      - AST走査時にLIMIT句やウィンドウ関数を持たないサブクエリ/CTE内にORDER BYが存在するとき、システムは `SNOW-003` 警告を出力しなければならない。

- 要件 A-5: インラインサブクエリの検出 (SNOW-007)
   - ユーザーストーリー
      - 私はデータエンジニアとして、FROM句やJOIN句にネストしたインラインサブクエリを検知したい。なぜならCTEに平坦化して可読性を高めるためだ。
   - 受け入れ基準
      - AST走査時にFROM句またはJOIN句に直接記述されたサブクエリ（Derived Table）が存在するとき、システムは `SNOW-007` 検出項目として記録しなければならない。

- 要件 A-6: UNIONの重複排除不要箇所の検出 (SNOW-006)
   - ユーザーストーリー
      - 私はデータエンジニアとして、重複排除（DISTINCTソート）が不要な箇所で使われている `UNION` を検知したい。なぜなら無駄なソートコストを削減するためだ。
   - 受け入れ基準
      - AST走査時に明示的な重複排除が不要な結合箇所で `UNION`（`distinct=True`）が使用されているとき、システムは `SNOW-006` 警告として検出し、`UNION ALL` への置換候補を提示しなければならない。

- 要件 A-7: 暗黙のクロス結合の検出 (SNOW-004)
   - ユーザーストーリー
      - 私はデータエンジニアとして、FROM句にカンマ区切りでテーブルが並べられているクエリを検知したい。なぜなら直積（Cartesian Product）による意図しないメモリ爆発事故を防ぐためだ。
   - 受け入れ基準
      - AST走査時にFROM句にカンマ区切りで複数のテーブル参照（`exp.From` 内の複数テーブル）が存在するとき、システムは `SNOW-004` 警告として検出し、明示的な `CROSS JOIN` または `INNER JOIN ... ON` への書き換えを警告しなければならない。

- 要件 A-8: 複数CTE間での同一テーブル重複スキャンの検出 (SNOW-005)
   - ユーザーストーリー
      - 私はDBAとして、複数のCTEで同一テーブルが個別にフルスキャンされている冗長なクエリを検知したい。なぜならマイクロパーティション再スキャンコストを削減するためだ。
   - 受け入れ基準
      - AST走査時に同一クエリ内の2つ以上のCTE定義で同一のベーステーブルが参照されているとき、システムは `SNOW-005` 警告として検出し、共通CTEへの集約を推奨しなければならない。

### 要件カテゴリB: AST In-place 置換とリファクタリング

- 要件 B-1: 決定論的ルールによるノード置換
   - ユーザーストーリー
      - 私はデータエンジニアとして、定型的なアンチパターンをルールベースで安全に自動置換したい。なぜなら100%安全かつ瞬時に修正するためだ。
   - 受け入れ基準
      - ユーザーが自動修正を指示したとき、システムは `SNOW-001`（Sargable範囲条件化）および `SNOW-003`（ORDER BYノード削除）をAST上で直接置換しなければならない。

- 要件 B-2: インラインサブクエリのトップレベルCTE外出し
   - ユーザーストーリー
      - 私はデータエンジニアとして、ネストしたサブクエリを命名されたCTEに自動変換したい。なぜなら上から下へ流れるパイプライン構造に整理するためだ。
   - 受け入れ基準
      - ユーザーがサブクエリ平坦化を指示したとき、システムはインラインサブクエリの内部SELECTを抽出し、一意な名前を持つCTEとしてトップレベルのWITH句に昇格させ、元の出現箇所をシンプルなテーブル参照に置換しなければならない。

- 要件 B-3: 局所スライスとLLMによるピンポイントリライト
   - ユーザーストーリー
      - 私はデータエンジニアとして、複雑な相関副クエリの書き換えをLLMに安全に依頼したい。なぜならクエリ全体のセマンティクスを壊さずに高度な最適化を行うためだ。
   - 受け入れ基準
      - ユーザーがLLMリライトを選択したとき、システムは該当サブツリーと最小限のスキーマ情報のみを抽出してプロンプトを構築し、LLMが返した置換コードを部分パースして構文検証した上で、元のASTノードと差し替えなければならない。
      - Vertex AI 接続時、ロケーションが `global` の場合は `aiplatform.googleapis.com` を、特定リージョンの場合は `{location}-aiplatform.googleapis.com` をホストとして使用しなければならない。
      - Vertex AI 利用時に ADC 資格情報ライブラリによるトークン取得が行えない場合、システムは `gcloud.cmd`（Windows）または `gcloud` の `auth application-default print-access-token` を呼び出してトークン取得をフォールバック試行しなければならない。

- 要件 B-4: UNIONからUNION ALLへの置換 (SNOW-006)
   - ユーザーストーリー
      - 私はデータエンジニアとして、検出された `UNION` を安全に `UNION ALL` へ自動置換したい。なぜなら重複排除ソートの負荷を排除するためだ。
   - 受け入れ基準
      - ユーザーが自動修正を指示したとき、システムは `SNOW-006` で検出された `exp.Union` ノードの `distinct` 属性を False に変更し、`UNION ALL` として構文木を再構築しなければならない。

- 要件 B-5: 暗黙クロス結合から明示的JOINへの置換 (SNOW-004)
   - ユーザーストーリー
      - 私はデータエンジニアとして、カンマ区切りのFROM句を明示的な `CROSS JOIN` 構文に自動置換したい。なぜなら直積リスクを可視化し可読性を向上させるためだ。
   - 受け入れ基準
      - ユーザーが自動修正を指示したとき、システムは `SNOW-004` で検出されたカンマ結合テーブルを明示的な `exp.Join(kind="CROSS")` ノードに置換しなければならない。

### 要件カテゴリC: 処方箋駆動最適化パイプライン (diag / diff / fix)

- 要件 C-1: 構造化処方箋診断コマンド (`icepick diag`)
   - ユーザーストーリー
      - 私はデータエンジニアまたはAIコーディングエージェントとして、長大なSnowflake SQLから改善点と具体的な修正指示（処方箋）を構造化データとして取得したい。なぜなら無駄なクエリ全文再フォーマットを避け、ピンポイントな修正箇所のみを把握・判断するためだ。
   - 受け入れ基準
      - ユーザーまたはエージェントが `icepick diag <file>` を実行したとき、システムは `sqlglot` を用いてASTおよびセマンティクス診断を実行し、各指摘事項に一意な処方箋ID（例: `RX-001`）と修正指示（アクション、対象ノード、修正前後のSQL断片、理由、期待効果）を含む処方箋リストをターミナル上にカード形式で表示しなければならない。
      - ユーザーまたはエージェントが `--format json` オプションを指定して `icepick diag <file> --format json` を実行したとき、システムは標準化されたJSONスキーマに準拠した処方箋データを標準出力に出力しなければならない。
      - 入力SQLに構文エラーが含まれるとき、システムはエラー発生箇所の行番号を出力し、非ゼロの終了コードで終了しなければならない。

- 要件 C-2: 処方箋ID選択型差分生成コマンド (`icepick diff`)
   - ユーザーストーリー
      - 私はデータエンジニアまたはAIコーディングエージェントとして、`diag` で提示された処方箋の中から適用したい項目のみを選択して、元ファイルの書式を壊さない最小限のGit互換Unified Diffを生成したい。なぜなら安全に段階的なリファクタリングをレビュー・検証するためだ。
   - 受け入れ基準
      - ユーザーが `icepick diff <file>` を実行したとき、システムは検出された全処方箋を元テキスト上に局所反映したUnified Diffを標準出力に表示しなければならない。
      - ユーザーが `--rx <id_list>`（例: `--rx RX-001,RX-003`）を指定して `icepick diff <file> --rx RX-001` を実行したとき、システムは指定された処方箋IDのみを適用対象として絞り込み、その他の箇所は1文字も変更しない局所差分を生成しなければならない。
      - 存在しない処方箋IDが `--rx` に指定されたとき、システムは有効な処方箋IDの一覧とエラーメッセージを出力し、非ゼロの終了コードで終了しなければならない。

- 要件 C-3: 処方箋ID選択型ファイル適用コマンド (`icepick fix`)
   - ユーザーストーリー
      - 私はデータエンジニアとして、生成された処方箋または差分を元ファイルに安全にインプレース適用したい。なぜなら手動でコピペする手間を省くためだ。
   - 受け入れ基準
      - ユーザーが `icepick fix <file>` を実行したとき、システムは処方箋を元ファイルへ直接書き換えて適用しなければならない。
      - ユーザーが `--rx <id_list>` を指定して `icepick fix <file> --rx RX-001` を実行したとき、システムは指定された処方箋IDのみを元ファイルへインプレース適用し、未指定の箇所は一切変更してはならない。
      - ユーザーが `--dry-run` を指定したとき、システムはファイルを一切変更せず、適用シミュレーション結果のみを出力しなければならない。

- 要件 C-4: LLM/Agentic 局所リライト (`icepick diag/diff --agentic`)
   - ユーザーストーリー
      - 私はデータエンジニアまたはAIコーディングエージェントとして、ルールベースで置換できない複雑な相関副クエリや共通CTE集約などの課題を、Gemini/Vertex AIの局所リライトにより安全に自動リライトしたい。なぜならセマンティクスを壊さずに高度なクエリ最適化処方箋を生成するためだ。
   - 受け入れ基準
      - ユーザーまたはエージェントが `--agentic` オプションを指定して実行したとき、システムは `requires_llm=True` とマークされた診断課題を抽出し、`ContextSlicer` で最小限の構文コンテキストを切り出して `LLMClient`（Gemini / Vertex AI REST API）に局所リライトを要求しなければならない。
      - `--provider`（`-p`）または `--model`（`-m`）オプションが指定されたとき、システムは設定ファイルや環境変数よりも優先して指定されたプロバイダ（`gemini` または `vertex`）およびモデルを使用しなければならない。
      - もし LLM から返却された SQL スニペットの構文解析時に構文エラーが発生した場合、システムは元の AST ノードを維持して安全にフォールバックしなければならない。

- 要件 C-5: 元ソース書式保持と最小Diff生成 (Source-Preserving Targeted Diff)
   - ユーザーストーリー
      - 私はエンタープライズ環境のデータエンジニアとして、元のSQLファイルのインデント、コメント、改行、大文字小文字スタイルを1文字も壊さずに、最適化された患部のみを局所置換した最小限のUnified Diffを生成したい。なぜならレビュー負荷を極小化し、パッチを確実に適用するためだ。
   - 受け入れ基準
      - ユーザーが `icepick diff <file>` を実行したとき、システムはクエリ全体のAST再フォーマットによるDiff生成を行わず、元の生ソースコードから患部ノードの該当テキストのみを局所置換した生テキスト差分をUnified Diffとして生成しなければならない。
      - ユーザーが `icepick fix <file>` で適用するとき、システムは元のソースファイルのインデントやコメント配置を完全維持し、行不一致エラーを起こすことなく外科手術的に適用できなければならない。


### 要件カテゴリD: 決定論的等価性検証 SQL 生成 (Verifier SQL Generator)

- 要件 D-1: 双方向 EXCEPT 等価性検証 SQL 生成コマンド (`icepick verify`)
   - ユーザーストーリー
      - 私はデータエンジニアまたはAIコーディングエージェントとして、最適化前後の2つのクエリが同一の実行結果を返すことを確認するための双方向 EXCEPT クエリを決定論的に生成したい。なぜなら本番 Snowflake への直接接続権限や重厚なドライバを持たない環境でも、公式 CLI（`snow CLI`）等とパイプ連携して安全かつ軽量に等価性を検証するためだ。
   - 受け入れ基準
      - ユーザーまたはエージェントが `icepick verify <original_file> <optimized_file>` を実行したとき、システムは両クエリを安全に読み込み、意味的に等価であれば 0 行を返す双方向 EXCEPT クエリ（`orig EXCEPT opt` および `opt EXCEPT orig` の UNION ALL）を標準出力に出力しなければならない。
      - `-o, --output <file>` オプションが指定されたとき、システムは生成された検証 SQL を指定されたファイルパスに保存しなければならない。
      - `--count-only` フラグが指定されたとき、システムは行データそのものではなく、各方向の差分件数のみを集計するクエリ（`SELECT 'orig_not_in_opt' AS diff_type, COUNT(*) AS cnt ...`）を生成して出力しなければならない。
      - システムはクエリ検証のために Snowflake データベースへの直接ネットワーク接続や認証情報の要求を行ってはならず、純粋なローカル SQL 生成ツールとして動作しなければならない。
      - 構文エラーやファイル読み込み失敗が発生したとき、システムはエラー原因を明記したエラーメッセージを標準エラー出力（stderr）に出力し、非ゼロ終了コードで終了しなければならない。

### 要件カテゴリE: エージェント親和性・フィードバックループ・セキュア認証 (Agent-Native DX)

- 要件 E-1: フィードバック記録コマンド (`icepick feedback`)
   - ユーザーストーリー
      - 私はAIコーディングエージェントまたは開発者として、テストや運用中に遭遇した摩擦（フリクション）、バグ、改善アイデアを即座にローカルログへ記録したい。なぜならツールの改善サイクルを円滑に回すためだ。
   - 受け入れ基準
      - ユーザーまたはエージェントがメッセージを指定して `icepick feedback <message>` を実行したとき、システムはタイムスタンプ（ISO 8601）、バージョン、カテゴリ、CWD を付与し、ローカルログファイル（`.icepick_feedback.jsonl`）に JSON Lines 形式で安全に追記しなければならない。
      - `--category` オプションが指定されたとき、システムは `friction`, `bug`, `doc`, `idea` のいずれかを受け入れなければならず、不正な値が渡されたときは有効な enum 一覧を提示して非ゼロ終了コードで終了しなければならない。
      - `--json` フラグが指定されたとき、システムは記録結果（ステータス、保存先パス、記録エントリ）を JSON 形式で標準出力しなければならない。

- 要件 E-2: 機械判読可能な構造化出力 (`--json` フラグ)
   - ユーザーストーリー
      - 私はAIコーディングエージェントとして、診断結果や適用結果をプログラムからパースしやすい JSON で受け取りたい。なぜなら装飾テキストのパースミスやトークン浪費を防ぐためだ。
   - 受け入れ基準
      - ユーザーまたはエージェントが各サブコマンド（`check`, `rewrite`, `patch` 等）で `--json` フラグを指定したとき、システムは ANSI エスケープ装飾や整列テーブルを排除し、構造化された JSON データを標準出力（stdout）に出力しなければならない。
      - 診断・実行ログやエラー情報は標準エラー出力（stderr）に分離して出力しなければならない。

- 要件 E-3: 非対話型の徹底とTTY判定
   - ユーザーストーリー
      - 私はAIコーディングエージェントとして、パイプラインや非対話シェルでツールを実行した際に、対話プロンプトでプロセスがハングすることを防ぎたい。なぜなら自律実行のタイムアウト事故を防止するためだ。
   - 受け入れ基準
      - 標準入力（stdin）が対話型ターミナル（TTY）でない環境で実行されたとき、システムはユーザー入力を待つ対話プロンプトを表示して停止してはならず、自動的に非対話モードとして安全に処理を完了するか、明確なエラーメッセージを出力して終了しなければならない。

- 要件 E-4: セキュアなクレデンシャル解決（Gemini API キーの WCM 管理と優先順位ピラミッド）
   - ユーザーストーリー
      - 私はセキュリティ管理者および開発者として、LLM の API キーが設定ファイルや環境変数に分散して混ざる混乱を防ぎ、OS ネイティブの安全なストレージで管理させたい。なぜなら秘密情報の漏洩や設定の断片化による誤動作・事故を防ぐためだ。
      - *(※ ADR-0004 により Snowflake 接続責任を外部公式ツールへ委ねたため、Snowflake 認証情報の管理は不要化)*
   - 受け入れ基準
      - システムが Gemini API キー（`gemini_api_key`）を解決するとき、汎用環境変数は無視し、以下の厳格な優先順位に従って探索しなければならない：
         1. デバッグ/CI専用環境変数（`DEBUG_ICEPICK_GEMINI_API_KEY`）
         2. Windows 資格情報マネージャー（Target: `icepick:gemini_api_key`）
      - Windows 資格情報マネージャーから読み込むとき、システムは `cmdkey` による UTF-16LE（null バイト混入）を自動判定して正常な文字列にデコードしなければならない。
      - Gemini API キーが WCM およびデバッグ環境変数のいずれからも解決できないとき、システムはシェル履歴に平文を残さない安全な PowerShell 登録例（`Get-Credential` 経由）および `cmdkey` 例を含む自己修正エラー（Actionable Error）を出力して異常終了しなければならない。

- 要件 E-5: 機械可読イントロスペクション (`icepick agent-context`)
   - ユーザーストーリー
      - 私はAIコーディングエージェントとして、ツールの全コマンド体系・引数スキーマ・全最適化ルール一覧・設定可能変数を1回のコマンド実行で構造化データとして把握したい。なぜなら何度も `--help` を実行する試行錯誤とトークン消費を抑えるためだ。
   - 受け入れ基準
      - ユーザーまたはエージェントが `icepick agent-context` を実行したとき、システムは CLI のバージョン、全コマンドと引数の定義、有効な最適化ルール一覧、および環境変数スキーマを含む JSON 構造を標準出力に出力しなければならない。

- 要件 E-6: 破壊的操作の明示的境界 (`--dry-run` & `--force`)
   - ユーザーストーリー
      - 私はAIコーディングエージェントまたは開発者として、最適化結果をファイルへ直接書き換える前に安全にプレビューし、誤操作による上書き事故を確実に防ぎたい。
   - 受け入れ基準
      - ユーザーまたはエージェントがファイル変更を伴うコマンド（`patch`）を実行する際、`--dry-run` フラグが指定されたときはファイルを一切変更せず、適用シミュレーション結果のみを出力しなければならない。
      - 標準入力が非TTYの環境で `icepick patch` によるファイル更新を行う場合、明示的な確認バイパスフラグ（`--force`）が指定されない限りファイル書き換えを拒否し、Actionable なエラーメッセージを案内して非ゼロ終了しなければならない。

- 要件 E-7: 自己修正を導く引数エラーと許容値提示
   - ユーザーストーリー
      - 私はAIコーディングエージェントとして、引数やオプションの指定を誤った際に、即座に正しい選択肢を把握して自己修正したい。
   - 受け入れ基準
      - ユーザーまたはエージェントが無効な引数（未定義のルール名、不正なカテゴリ名、未対応の出力フォーマット等）を指定したとき、システムは単にエラーを返すだけでなく、受け入れ可能な全選択肢（enumリスト）および正しいコマンド例をエラーメッセージに含めなければならない。

- 要件 E-8: エージェント準備状況テスト (Agent Readiness Test)
   - ユーザーストーリー
      - 私は品質保証エンジニアとして、CLIがエージェント環境下でハングせず安全に動作することを自動テストで恒久的に保証したい。
   - 受け入れ基準
      - テストスイートを実行したとき、標準入力非TTY時のハング防止、全サブコマンドの `--json` 出力の妥当性、未認証時のActionable Error出力がすべて合格しなければならない。

- 要件 E-9: マルチソース設定解決と実行時コンフィグ・フィードバック (Active Configuration Feedback)
   - ユーザーストーリー
      - 私はデータエンジニアまたはAIコーディングエージェントとして、実行時にどのLLMプロバイダ（Gemini / Vertex AI）・GCPプロジェクト・モデル・認証ソースがアクティブになっているかを明確に把握したい。なぜなら意図しない環境（個人環境 vs 会社環境）や設定の不整合による事故を防ぐためだ。
   - 受け入れ基準
      - システムがLLM設定を解決するとき、以下の優先順位（1. CLIオプション、2. 環境変数、3. 設定ファイル、4. セキュア認証情報 (KEYRING)、5. 組み込みデフォルト）に従ってカスケードマージし、各パラメータの解決元ソース（CLI / Env / File / Keyring / Default）を特定しなければならない。
      - `--agentic` を指定して実行したとき、システムはアクティブなLLM設定サマリー（プロバイダ、モデル、GCPプロジェクト、ロケーション、認証方式、解決元ソース）をターミナルに表示しなければならない。
      - `--json` フラグが指定されたとき、システムは出力JSONのルート要素に `runtime_config` オブジェクトを含め、適用された設定値と解決元ソースを機械可読に出力しなければならない。
      - ユーザーまたはエージェントが `icepick config show` を実行したとき、システムは現在解決されている全設定項目（LLM設定、Dialect設定、ルール設定）とその解決元ソースの一覧テーブルを表示しなければならない。

- 要件 E-10: LLM 接続診断・ヘルスチェックコマンド (`icepick config test`)
   - ユーザーストーリー
      - 私はデータエンジニアまたはAIコーディングエージェントとして、最適化を実行する前に、LLM（Gemini / Vertex AI）の接続設定が正しいかを事前に確認したい。なぜなら本番クエリの最適化途中で認証エラーやネットワーク不通による失敗を防ぐためだ。
   - 受け入れ基準
      - ユーザーまたはエージェントが `icepick config test` を実行したとき、システムは設定された LLM プロバイダの認証妥当性およびネットワーク疎通を検証しなければならない。
      - システムが LLM 接続を検証するとき、アクティブな設定（プロバイダ、モデル、GCPプロジェクト、ロケーション、認証方式）を解決し、最小限のテストプロンプトを送信して応答が得られることを検証しなければならない。
      - 接続診断を実行したとき、システムは成否（PASS / FAIL）、応答時間（ミリ秒）、および接続先メタデータ（プロバイダ/モデル名、プロジェクト/ロケーション等）をターミナルにわかりやすく表示しなければならない。
      - 接続に失敗したとき、システムは失敗原因と具体的な復旧手順（Actionable Advice、WCM 登録コマンド例や `gcloud` 認証例）を表示し、終了コード 1 で終了しなければならない。
      - `--json` フラグが指定されたとき、システムはチェック結果（ステータス、応答時間、メタデータ、エラー詳細）を含む機械可読な構造化 JSON を標準出力に出力しなければならない。
      - チェックが成功したとき、システムは終了コード 0 で正常終了しなければならない。

### 要件カテゴリF: 拡張可能なプラガブルLLMプロバイダ基盤 (Pluggable LLM Providers)

- 要件 F-1: プラガブルLLMプロバイダ分離と設定汎化 (Pluggable Providers & Generic Config)
   - ユーザーストーリー
      - 私は開発者またはシステム管理者として、LLMプロバイダ（Gemini / Vertex AI、および将来のプロバイダ）の実装が独立したモジュールに分離され、プロバイダ固有の設定が辞書形式（`dict`）で柔軟に渡せるようにしたい。なぜならコードベースの結合度を下げ、新しいLLMプロバイダの追加や環境ごとの異なる設定への対応を容易にするためだ。
   - 受け入れ基準
      - システムがLLMリクエストを実行するとき、システムはプロバイダ種別（`gemini`, `vertex` 等）に応じて独立したプロバイダモジュールへ処理を委譲し、テキスト生成およびASTリライトを実行しなければならない。
      - システムがLLMプロバイダを初期化するとき、プロバイダごとに異なる個別設定（APIキー、GCPプロジェクト、リージョン、エンドポイント、追加パラメータ等）を汎用的な辞書形式（`dict[str, Any]`）の設定として透過的に受け入れ、各プロバイダに引き渡さなければならない。
      - 未知のプロバイダ名が指定されたとき、システムは利用可能なサポート対象プロバイダ一覧を明記したエラーメッセージを提示して安全に例外を送出しなければならない。
      - LLMプロバイダの抽象基底（または共通インターフェース）に準拠した新規プロバイダクラスを追加したとき、既存のクライアント呼び出し側（CLI、Health Check、Agentic Patcher）のロジックを変更することなくシームレスに機能拡張できなければならない。

- 要件 F-2: Vertex AI 呼び出し仕様の堅牢化とエージェント向け明示的プロバイダ案内 (Robust Vertex AI Invocation & Actionable Provider Guidance)
   - ユーザーストーリー
      - 私はAIコーディングエージェントまたはデータエンジニアとして、Vertex AI環境で安定してクエリ最適化を実行したいとともに、プロバイダ設定が不足している場合に暗黙の推論による混乱を避け、明確かつ具体的な指定指示を受け取りたい。なぜならエージェントの自律実行時の誤動作や環境の取り違えを防止するためだ。
   - 受け入れ基準
      - システムが Vertex AI REST API を呼び出すとき、リクエストの `contents` 内に `role: "user"` を明示的に含め、スキーマ不一致エラーを防止しなければならない。
      - システムが Vertex AI のレスポンスを解析するとき、`candidates[0].content.parts` 内のすべてのテキストブロックを走査・集約し、思考モデルや複数パートに分かれた出力を漏れなく抽出しなければならない。
      - ユーザーまたはエージェントがプロバイダを明示的に指定せず（デフォルトの `gemini`）、かつ Gemini API キーが未解決のとき、システムは暗黙の自動フォールバックを行わず、現在のプロバイダがデフォルトの `gemini` である旨と、Vertex AI を使用する場合の明示的指定方法（CLI オプション `--provider vertex`、環境変数 `ICEPICK_LLM_PROVIDER=vertex`、設定ファイル `.icepick.toml` の `llm_provider = "vertex"`）を含む Actionable な案内を出力して終了しなければならない。
      - ユーザーまたはエージェントが `icepick config test` を実行するとき、システムは `--provider` (`-p`) および `--model` (`-m`) オプションによるテスト対象プロバイダ・モデルの明示指定を受け入れ、指定されたプロバイダのヘルスチェックを直接実行しなければならない。
