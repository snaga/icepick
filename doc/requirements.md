## 概要

本システム（Icepick for Snowflake、CLI名: icepick）は、Snowflake環境で実行される長大バッチクエリに対し、AST（抽象構文木）を用いた決定論的なアンチパターン診断と、ピンポイントなIn-place置換（ルールベースおよび局所LLM連携）を実施し、Git互換のUnified Diff形式で差分を提示・適用するCLIツールである。

## 前提条件

- 入力されるSQLは、Snowflakeの方言（Dialect）として構文的に有効であること。
- Python 3.10以上の実行環境および `sqlglot` ライブラリが利用可能であること。
- LLMによる局所リライト機能を利用する場合、有効なLLM APIキーが環境変数に設定されていること。
- Snowflake上での等価性検証機能を利用する場合、有効なSnowflake接続認証情報が設定されていること。

## 制約条件

- 構文エラーを持つ入力SQLに対しては、ファイルを変更せず明確なエラー行番号を出力して終了しなければならない。
- 最適化処理において、対象外の健全なASTノードの構文構造・論理セマンティクスを一切破壊してはならない。
- 差分出力は、標準的なGit diffツール（`git apply` 等）で解釈可能なUnified Diff形式に厳格に準拠しなければならない。

## 要件

### 要件カテゴリA: 構文解析と決定論的静的診断 (Linter)

- 要件 A-1: Snowflake SQLパース
   - ユーザーストーリー
      - 私はデータエンジニアとして、Snowflake特有の構文を含むSQLファイルを読み込みたい。なぜなら正確な構文木として解析するためだ。
   - 受け入れ基準
      - ユーザーがSQLファイルパスを指定して `icepick check <file>` を実行したとき、システムは `sqlglot` を用いてSnowflake方言としてASTを構築しなければならない。
      - もし入力SQLに構文エラーが含まれる場合、システムはエラー発生箇所の行番号とトークン情報を表示し、非ゼロの終了コードで終了しなければならない。

- 要件 A-2: Non-Sargable述語の検出 (SNOW-001)
   - ユーザーストーリー
      - 私はデータエンジニアとして、パーティションプルーニングを無効化しているWHERE句を検知したい。なぜなら無駄なフルスキャンを防ぐためだ。
   - 受け入れ基準
      - AST走査時にWHERE句内のカラムに対する関数適用比較（例: `DATE(col) = '...'`）が存在するとき、システムは `SNOW-001` 警告として該当ノードの行番号とコードスニペットを出力しなければならない。

- 要件 A-3: 相関副クエリの検出 (SNOW-002)
   - ユーザーストーリー
      - 私はDBAとして、反復評価やメモリSpillを引き起こす相関副クエリを検知したい。なぜならクエリ実行時間の爆発を避けるためだ。
   - 受け入れ基準
      - AST走査時に外側テーブルのエイリアスを参照するサブクエリ（Correlated Subquery）が存在するとき、システムは `SNOW-002` 警告として重度 `CRITICAL` で出力しなければならない。

- 要件 A-4: サブクエリ内の不要なソートの検出 (SNOW-003)
   - ユーザーストーリー
      - 私はデータエンジニアとして、サブクエリ内にある無意味なORDER BYを検出したい。なぜならオプティマイザの負荷とメモリ消費を削減するためだ。
   - 受け入れ基準
      - AST走査時にLIMIT句やウィンドウ関数を持たないサブクエリ/CTE内にORDER BYが存在するとき、システムは `SNOW-003` 警告を出力しなければならない。

- 要件 A-5: インラインサブクエリの検出 (SNOW-007)
   - ユーザーストーリー
      - 私はデータエンジニアとして、FROM句やJOIN句にネストしたインラインサブクエリを検知したい。なぜならCTEに平坦化して可読性を高めるためだ。
   - 受け入れ基準
      - AST走査時にFROM句またはJOIN句に直接記述されたサブクエリ（Derived Table）が存在するとき、システムは `SNOW-007` 検出項目として記録しなければならない。

### 要件カテゴリB: AST In-place 置換とリファクタリング

- 要件 B-1: 決定論的ルールによるノード置換
   - ユーザーストーリー
      - 私はデータエンジニアとして、定型的なアンチパターンをルールベースで安全に自動置換したい。なぜなら100%安全かつ瞬時に修正するためだ。
   - 受け入れ基準
      - ユーザーが自動修正を指示したとき、システムは `SNOW-001`（Sargable範囲条件化）および `SNOW-003`（ORDER BYノード削除）をAST上で直接置換しなければならない。

- 要件 B-2: インラインサブクエリのトップレベルCTE外出し
   - ユーザーストーリー
      - 私はデータエンジニアとして、ネストしたサブクエリを命名されたCTEに自動変換したい。なぜなら上から下へ流れるパイプライン構造に整理するためだ。
   - 受け入れ基準
      - ユーザーがサブクエリ平坦化を指示したとき、システムはインラインサブクエリの内部SELECTを抽出し、一意な名前を持つCTEとしてトップレベルのWITH句に昇格させ、元の出現箇所をシンプルなテーブル参照に置換しなければならない。

- 要件 B-3: 局所スライスとLLMによるピンポイントリライト
   - ユーザーストーリー
      - 私はデータエンジニアとして、複雑な相関副クエリの書き換えをLLMに安全に依頼したい。なぜならクエリ全体のセマンティクスを壊さずに高度な最適化を行うためだ。
   - 受け入れ基準
      - ユーザーがLLMリライトを選択したとき、システムは該当サブツリーと最小限のスキーマ情報のみを抽出してプロンプトを構築し、LLMが返した置換コードを部分パースして構文検証した上で、元のASTノードと差し替えなければならない。

### 要件カテゴリC: Unified Diff 出力と対話型レビュー

- 要件 C-1: カラーUnified Diffプレビュー
   - ユーザーストーリー
      - 私はデータエンジニアとして、最適化前後の差分をGit diff形式で確認したい。なぜなら意図しない変更が含まれていないか一瞬でレビューするためだ。
   - 受け入れ基準
      - 最適化コードが生成されたとき、システムは変更前のフォーマット正規化コードと最適化後コードのUnified Diffを生成し、ターミナル上にカラーハイライトで表示しなければならない。

- 要件 C-2: Hunkごとのインタラクティブ適用
   - ユーザーストーリー
      - 私はデータエンジニアとして、複数の変更箇所を1つずつ確認しながら適用可否を選びたい。なぜなら納得のいく変更だけを採用するためだ。
   - 受け入れ基準
      - 対話モード（`--interactive`）で実行されたとき、システムは変更箇所（Hunk）ごとにDiffを提示し、ユーザーのキー入力（`[y]` 適用, `[n]` スキップ, `[q]` 中断）に応じて適用を制御しなければならない。

- 要件 C-3: パッチファイル保存およびファイル書き込み
   - ユーザーストーリー
      - 私はデータエンジニアとして、生成されたDiffをファイルに直接適用するか、パッチファイルとして保存したい。なぜならチームレビューやCI連携に活用するためだ。
   - 受け入れ基準
      - `--write` フラグが指定されたとき、システムは変更内容を入力ファイルに直接上書き保存しなければならない。
      - `--patch <path>` が指定されたとき、システムはUnified Diffの内容をパッチファイルとして保存しなければならない。

### 要件カテゴリD: 決定論的等価性自動検証 (Verifier)

- 要件 D-1: EXCEPT 差分ゼロ検証
   - ユーザーストーリー
      - 私はデータエンジニアとして、最適化後のクエリが元クエリと1行も違わず同一の結果を返すことを証明したい。なぜなら本番データ破壊を確実に防ぐためだ。
   - 受け入れ基準
      - ユーザーが `--verify` フラグを指定して実行したとき、システムはSnowflakeに対して元クエリと最適化クエリの双方向 `EXCEPT`（差分抽出）を実行し、両方の差分カウントが0である場合のみ「検証合格」と判定しなければならない。
